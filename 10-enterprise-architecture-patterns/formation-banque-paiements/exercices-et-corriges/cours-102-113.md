## Étude transverse — banque fictive, virement SEPA de 500 EUR
Le client initie un ordre avec référence immuable. Un composant perd sa réponse après commit, un message est redélivré et une vue de reporting présente un statut en retard.

**Travail attendu :**
1. Dessiner un schéma AS-IS et un schéma cible ; définir la source autoritative des statuts.
2. Identifier les identités techniques (messageId, correlationId) et la référence métier d'idempotence.
3. Produire la séquence nominale, un refus, un timeout, une livraison répétée et une reprise.
4. Expliquer précisément l'absence de double effet financier, malgré concurrence et redémarrages.
5. Documenter les SLO, limites de rétention, confidentialité, décisions d'architecture et preuves de test.

**Erreurs éliminatoires :** considérer un ACK Kafka/MQ comme un règlement, traduire un timeout en rejet certain, utiliser un snapshot analytique comme source de paiement, ou prétendre qu'un mécanisme de HA suffit à empêcher le split-brain.

## Épreuve de synthèse
**Q1.** Après commit, le client perd sa réponse : A / Retenter avec une référence aléatoire ; B / Retrouver le statut via la référence stable ; C / Marquer le paiement rejeté. **Réponse B.**

**Q2.** Une projection est plus ancienne que le core : A / Prendre la projection comme preuve financière ; B / Corriger le core depuis la projection ; C / Afficher sa fraîcheur et consulter la source autoritative pour les décisions critiques. **Réponse C.**

**Q3.** Deux writers écrivent après une bascule : A / Mettre en place une exclusivité prouvée (fencing, propriétaire ou quorum selon architecture) ; B / Considérer les pods Running comme garantie ; C / Dupliquer chaque demande pour augmenter la disponibilité. **Réponse A.**
